# The PDF page's changes as plans

Pull request [#70](https://github.com/drthyang/web-refinement/pull/70),
branch `claude/pdf-plans`, stacked on `claude/tool-facts` ([#69](https://github.com/drthyang/web-refinement/pull/69)), 2026-10-18.
Plan: [AGENT_PLAN.md](../AGENT_PLAN.md), 3.1. The second half of the
architecture review's #4 (one definition per live tool), on its first page:
as the user answered Q1 b and Q2, one plan per tool per page in place of the
three switches, PDF first, the single-crystal and powder pages after it.

A change tool ran through three functions per page, each a switch on the
tool's name:
- one said whether the change would do nothing (`pdfNoOp`);
- one wrote the approval card's line (`describePdfChange`);
- one made the change (`changePdf`).

Each read the input again, untyped. The input was checked only in the last,
after the user had approved the card. Four tools (`set_free`, `refine`,
`reset_parameters`, `go_to_step`) had near-identical arms on all three pages.

## What changed, and why

| Change | What it answers |
| --- | --- |
| A change is a plan: nothing to do (and why), or the card's line with the change itself (`Plan`, `pages/types.ts`). The executor plans once, where it called the three | Three switches per page, each reading the input again |
| The PDF page's plans are one table, `PDF_PLANS` (`pdfTools.ts`), typed so that each plan receives its tool's input as the schema parses it (`InputOf`, from the definitions' literal types), and the table must hold a plan for every change tool of the page or it does not compile (`PageChangeTool`) | An untyped `input: any`, and nothing that failed when a tool had no arm |
| The plans every page shares are written once (`pages/plans.ts`): `freePlan`, `refinePlan` (with the page's own card line, any reason it cannot refine, and its notes after a fit), `resetPlan`, `goToPlan` | Near-identical arms on every page |
| A PDF change that cannot run is refused when it is planned, before its card: a window with max below min or outside the data, a unit given on the PDF page, a scan of a pattern that matches nothing, of a site that is not there or of an anion's bonds, a refinement or scan with nothing free | The user approved a card for a change that then failed |
| The single-crystal and powder pages keep their three switches for now, behind `switchedPlan`, so they behave exactly as before | They become plans in their own changes |

## Evidence

- **The plans say what the switches said.** For 15 calls on the GaTa₄Se₈
  page, the plan gave the same card line, or the same reason there is nothing
  to do, as the old `describePdfChange` and `pdfNoOp`: `set_free` (free, fix,
  all), `set_adp_model` (both ways), `set_fit_range` (a window, the default,
  one end), `refine` and its thorough mode, `boxcar_scan` (plain, and with
  `free`, `bonds` and both directions), `reset_parameters` (all, one) and
  `go_to_step`.
- **Before the card** (`agent/pages/plans.test.ts`). On the base branch, a
  window with max below min, a scan of the anion Se1's bonds, and a
  refinement with every parameter fixed each showed a card, then failed once
  approved: four cards for four calls. Now only the `set_free` before them
  asks, and each of the three is refused before its card with the same
  message.
- **Every PDF change tool has a plan**: the compiler holds it, and a test does
  too. The test against side lists of tool names (#69) lets a page's plan
  table through, since its type holds it to the definitions.
- **In the browser**, the three committed demo replays gave the same drawer
  text as before on this branch's dev server, the GaTa₄Se₈ boxcar scan and
  its report among them, with no page error.
- **Nothing else changed.** The text the model reads is the snapshot's. The
  executor, Stop, the evidence gate, the PDF scenarios and replays, and the
  live tools' contracts pass unchanged.

## What changes for users

On the PDF page, a change the Agent proposes that cannot run is refused
before you are asked to approve it. The Agent gets the same message it got
after the approval. Before, you approved a card for a change that then
failed.

## What it means for the validation

The model reads the same tools and, on these failures, the same errors. The
only difference: on the PDF page those errors come without an approval in
between. A run in ask mode sees one card fewer for each such call.
