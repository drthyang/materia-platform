# The k-search: mixed-sign k, the hkl range from the cell, one policy

Pull request [#90](https://github.com/drthyang/web-refinement/pull/90),
branch `claude/plan-4-3`, on `main`, 2026-10-19. Plan:
[AGENT_PLAN.md](../AGENT_PLAN.md), 4.3. AGENT_REVIEW's tool table: "No
mixed-sign k such as (¼, 0, −¼), which monoclinic and triclinic cells need.
The hkl range is fixed at ±4, too few for large cells." Its proposal 3: "add
mixed-sign k for low-symmetry lattices, and size the hkl range from the cell."

## What was wrong

`searchPropagationVector` (core/magnetic/kSearch.ts) is the k-search behind
the magnetic step's panel, the app's `search_propagation_vector` and MCP's.
It had three gaps.

1. **The grid's first octant only.** Each component of k ran over
   {0, ⅙, ¼, ⅓, ½}. With every metric angle at 90°, (¼ 0 ¼) and (¼ 0 −¼) put
   their satellites at the same d. In a monoclinic cell the h·l term of the
   metric tells them apart, and a triclinic cell needs every sign. The search
   could not propose (¼ 0 −¼).
2. **hkl within ±4.** Satellites were predicted about G with |h|, |k|, |l| ≤ 4.
   On an 18–20 Å cell that reaches d ≈ 2.6 Å, and a satellite at h = 7 was
   never predicted, so it could not be matched.
3. **Two policies.** The app searched with no Q cut and a tolerance of 0.5 % of
   d. MCP's `search_propagation_vector` set the relative tolerance itself but
   took the function's default Q cut of 6 Å⁻¹. Every peak below d = 1.05 Å
   that an MCP client passed was dropped, unannounced, before scoring.

## What changed

| Change | Where |
| --- | --- |
| In a cell with an angle off 90°, each grid point's sign variants (the first nonzero component kept positive, since k ≡ −k). A variant whose satellites fall where a kept k's do adds a tie, not a k, and is dropped. Labels show the sign: "(¼ 0 −¼)" | `signVariants`, `searchPropagationVector` |
| The hkl range along each axis reaches the smallest d searched: \|h\| = \|G·a\| ≤ a/d, plus one for k, up to ±24. An explicit `hklRange` still sets it. The panel's per-peak Δd (`satelliteMatchDeltas`) uses the same range | `hklRangeOf` |
| One option set, `K_SEARCH_DEFAULTS` (0.02 Å or 0.5 % of d, no Q cut), is the function's default. The app's step and MCP no longer pass their own. `maxQ` asks for a cut | `kSearch.ts`, `magneticStep.ts`, `mcp/tools.ts` |
| Every satellite is compared only with the peaks inside the tolerance window (binary search), and \|G ± k\|² comes from a table of G built once per search. Without that, the larger range would have made the search slow | `reflectionTable`, `satelliteDistances` |
| The descriptions (the app's and MCP's) and LIMITATIONS.md say so | `tools.ts`, `registry.ts` |

The ranking is unchanged: the matched (weighted) fraction, then the
simplest k, then the RMSD. The last tie-break now sums |components|, so a
variant does not rank ahead of the first-octant k it ties with.

The test that held the old default (`ignores high-Q peaks`) now asks for the
cut. The Cr₂WO₆ test's absolute-tolerance case passes `relativeTolerance: 0`,
since 0.5 % is now the default. The rest of the k-search tests pass as they
were: the AWO₄ cell (β = 89.3°, so it gets the variants too), the centred
lattice, and the satellite list.
