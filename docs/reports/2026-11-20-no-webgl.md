# Without WebGL the 3D view is a line in its card, not a page error

A user on Chrome / Ubuntu with WebGL unavailable loaded a CIF and the whole
workbench was replaced by "This structure and data cannot be calculated.
THREE.WebGLRenderer: Error creating WebGL context.", with only "Clear the
workbench" to press. Nothing was wrong with the structure or the data:
`StructureView` built a three.js renderer at two places with no guard, the
3D card is mounted as soon as a structure is loaded, and the constructor's
throw reached the workbench's error boundary. Refinement does not need WebGL.

This change makes a missing WebGL context a line in the 3D card. Layout and
display only: no numeric changes, and nothing the Copilot's model reads
changes (no tool description, skill, prompt or snapshot file).

## The audit

Every use of WebGL, three.js, WebGPU and `getContext` in `src`.

## What changed, and why

- **WebGL is asked for once** (`src/app/ui/webglSupport.ts`).
  `webglAvailable()` tries a "webgl2" context on a scratch canvas (three.js
  0.185 draws with WebGL 2 only), hands that context straight back, and
  remembers the answer for the page. It never throws. `createRenderer(make)`
  does not call three.js at all when the answer is no, and returns null when
  a constructor throws all the same.
- **The scene and the swatches are guarded** (`StructureView.tsx`). Without
  WebGL the scene effect does nothing and the card renders the line, the
  legend as dots and the host's downloads; the scene's knobs (bonds, light,
  finish, view a/b/c) are left out, as they have nothing to act on. The
  swatch renderer goes through `createRenderer`, and a failed swatch draw is
  caught, so a swatch can never take the scene down.
- **A lost context is said** (`StructureView.tsx`). `webglcontextlost` shows
  the "paused" line above the canvas; `webglcontextrestored` removes it and
  asks for a frame. The listeners are removed before the view's own
  `forceContextLoss` on cleanup.
- **A boundary around the 3D view** (`View3DBoundary` in
  `src/app/ui/View3DFallback.tsx`; `StructureView` is now the scene inside
  it). A three.js error from a render or an effect stays in the card. The
  workbench's boundary and its wording are not changed: a rendering failure
  can no longer reach it from the 3D view.
- **The line follows the UI text rule**: one plain line, result first, the
  detail behind "?" (and the line itself opens the "?", for a finger). The
  "?" says the rest of the app works, and how to check: `chrome://gpu`
  (Firefox `about:support`), graphics acceleration in the browser's
  settings, the graphics driver, another browser. The wording is "WebGL is
  not available in this browser", not "turned off": a blocked GPU or a
  browser with WebGL 1 only gets the same line, and it stays true.
- **Docs**: a "3D views" section in `docs/LIMITATIONS.md`, a sentence in the
  user guide, a changelog entry.

No file of the moments-alternation branch is touched; the magnetic page gets
the fix through `StructureView` itself.

## Evidence

- **Before, on the live site** (`main` at `7832daf`, Chromium with
  `--disable-gpu --disable-software-rasterizer`): loading the Mn₃Ga demo
  logs "THREE.WebGLRenderer: Error creating WebGL context." and
  "[status] calculation failed", the page is replaced by the banner, and the
  3D Model tab cannot be reached. The same with the CIF-only load.
- **Tests** (`src/app/ui/structureViewNoWebgl.dom.test.ts`, 9 tests in
  happy-dom, whose canvas gives no WebGL context, as the reporting browser).
  The probe answers false, once, and does not throw when `getContext`
  throws; it hands a granted context back. `createRenderer` does not call
  the constructor without WebGL and returns null when it throws.
  `StructureView` inside a `WorkbenchErrorBoundary` shows the line and its
  "?", no canvas, the legend as dots, a working CIF button, and logs no
  error (three.js is never asked). With the probe forced to yes, three.js
  throws its real "Error creating WebGL context." in the scene effect: the
  card shows "the model could not be drawn", the page banner does not
  appear, the CIF button still works. Without the change the two view tests
  fail with the page banner.
- **WebGL off, the built app** (Playwright 1.61.1, Chromium 149 headless,
  1440×900, `npm run build && vite preview`; `--disable-3d-apis`, where
  `getContext("webgl2")` and `("webgl")` are null). 15 steps, 123 checks,
  all pass, 75 s: start page and Copilot panel; Mn₃Ga neutron TOF load and
  Refine (wR 4.24 %); Validation; 3D Model (the line, its "?", dots, the
  card's CIF download); Posterior; History; Report, CIF, CSV, GSAS-II and
  FullProf bundles and Save project (six files); Magnetic analysis through
  the k-search, Rank, the starred candidate and Refine moments (the line in
  the moment preview, the card's mCIF), Continue, mCIF and Report;
  GaTa₄Se₈ X-ray G(r) load and Refine (Rw 8.12 %); 3D Model; Subgroups
  list, Tree, detail and Activate (I-4m2); the 3D modes view with All in 3D
  and a Refine in the subgroup (Rw 8.06 %); Posterior, History, Copilot;
  Report, CIF, CSV, PDFgui bundle and Save project; a CIF-only load
  (`examples/mcp/mno.cif`) and its 3D Model. No page banner, no uncaught
  page error, no failed request. Console: only the browser's own WebGPU
  warning "No available adapters." (the GPU chip asking for an adapter),
  three times. three.js logs nothing now, because it is never called.
- **A second way of having no WebGL** (`--disable-gpu
  --disable-software-rasterizer`, the short path: start, load, Refine, 3D
  Model, CIF-only load): 4 steps, 29 checks, all pass. Console: the
  browser's "Failed to create WebGPU Context Provider", twice.
- **WebGL on, nothing regressed** (the same 15 steps at 1440×900): Chromium
  and WebKit both pass, 117 checks each; every 3D canvas is shown and is not
  a flat fill (88–372 bytes per kilopixel as PNG), the legend swatches are
  rendered spheres, and wR 4.24 %, Rw 8.12 % and 8.06 % are the same as with
  WebGL off. Console in Chromium: the browser's "GPU stall due to
  ReadPixels" (the swatches, as before the change) and "No available
  adapters."; none in WebKit.
- **A context lost and given back** (Chromium, `WEBGL_lose_context` on the
  scene's canvas): the "paused" line appears; after `restoreContext` it
  goes and the canvas is the same image as before (same PNG size, 31 869
  bytes); no console error, no banner.
- The four cases ran in 247 s in all. Script, logs and screenshots are kept
  outside the repository (`~/.local/share/materia-qa/2026-11-20/webgl/`).

## What changes for users

- With WebGL unavailable the app opens and works: loading, refinement, the
  plots, Validation, Posterior, the magnetic analysis, Subgroups, History,
  every export and the Copilot. Each 3D card shows one line in place of the
  model, with the reason and how to check behind "?".
- With WebGL available nothing looks different, except that a context the
  browser drops is now announced in the card.
- The Agent and MCP clients see no change.

## What it means for the validation

Nothing: no engine, tool or model-read text is touched, and no pinned result
moves. `src/agent/__snapshots__` is unchanged.

## Not done

- **A drawing without WebGL.** The card says the view is unavailable; it does
  not draw the cell another way (SVG or a 2D canvas). On the PDF page the
  mode table's "▸ green arrows: …" line still names what would be drawn, with
  the largest shift, while no arrows can be shown.
- **The workbench boundary's wording.** "This structure and data cannot be
  calculated." is still what any other render error on a page gets. The 3D
  view can no longer reach it; rewording it for non-calculation errors is a
  separate, small change, waiting on the owner.
- **A failed load of the 3D view's code chunk** (offline after the first
  page) is not caught by the new boundary, which sits inside that chunk.
- **Firefox** cannot be launched here, and a real Chrome / Ubuntu machine
  with a blocked GPU was not at hand: the two Chromium switches above stand
  in for it. WebKit has no switch for WebGL off.
- **The single-crystal page** has no bundled public demo, so its 3D card was
  not walked in the browser; it mounts the same `StructureView`.
